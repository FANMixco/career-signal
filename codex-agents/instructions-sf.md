# SuccessFactors CV Autofill Workflow for Codex

## Goal

Automate the repetitive cleanup required by SAP SuccessFactors job applications.

The user provides a SuccessFactors application URL. Codex opens that URL in the browser. The user performs the login manually. After the user has successfully logged in, Codex continues in the same authenticated browser session, uploads `cv.pdf`, waits for SuccessFactors to finish parsing it, and then corrects the structured application fields using `cv_as_excel.xlsx` as the source of truth.

The workflow is intentionally split into two roles:

```text
USER
  provides SuccessFactors URL
  logs in manually
  completes MFA / SSO / CAPTCHA if required

CODEX
  opens the supplied URL
  waits while the user logs in
  resumes only after authentication is complete
  uploads cv.pdf
  waits for SuccessFactors parsing to finish
  reads cv_as_excel.xlsx locally
  replaces or corrects SuccessFactors structured CV data from Excel
  verifies the saved application against Excel
  stops before final submission unless explicitly instructed otherwise
```

---

## Required local files

The working folder must contain:

```text
cv.pdf
cv_as_excel.xlsx
SUCCESSFACTORS_AUTOFILL.md
```

Use these filenames unless the user explicitly provides different ones.

### `cv.pdf`

Purpose: attachment upload only.

The PDF is required because many SuccessFactors implementations force the applicant to upload a CV before the application can continue.

Codex must **not** use the PDF as the source for filling structured fields.

### `cv_as_excel.xlsx`

Purpose: authoritative structured CV database.

This workbook is the only source of truth for the CV sections managed by this workflow.

### SuccessFactors URL

The URL is supplied by the user at runtime. It is not stored permanently in this Markdown file.

Example user instruction:

```text
Open this application and fill it from my files:
https://company.example.com/careers/job/12345
```

---

## Non-negotiable rules

1. Open exactly the URL supplied by the user.
2. Do not ask for the user's SuccessFactors password.
3. Do not enter, store, read, or manage login credentials.
4. The user performs the login manually in the browser opened by Codex.
5. If SSO, MFA, CAPTCHA, QR approval, passkeys, security keys, or another authentication step appears, leave it to the user.
6. Continue only after the authenticated application session is available.
7. Upload `cv.pdf` when SuccessFactors requests a CV or resume.
8. Allow SuccessFactors to finish any automatic CV parsing before editing structured sections.
9. Treat all data generated by the SuccessFactors PDF parser as untrusted temporary data.
10. Read structured CV data only from `cv_as_excel.xlsx`.
11. Never use the uploaded PDF to reconstruct missing structured data.
12. Never keep an automatically parsed value merely because it looks plausible if Excel contains a different value.
13. Never invent information that is absent from Excel.
14. Only modify application fields that can be supported by `cv_as_excel.xlsx`.
15. Do not answer application specific questions such as salary expectations, work authorization, willingness to relocate, diversity questions, legal declarations, referrals, or notice periods unless the user separately provides the answer.
16. Do not submit the final application unless the user explicitly instructs Codex to submit it.

# Execution flow

## Phase 1: Receive the URL

The user provides the SuccessFactors job or application URL.

Codex must:

1. Open the supplied URL in the browser.
2. Wait for the page to load.
3. If the site redirects to a login page, leave the browser ready for the user.
4. Tell the user that login is ready.
5. Stop browser interaction until the user has finished authentication.

Do not attempt to log in on the user's behalf.

---

## Phase 2: User login handoff

The user logs in manually.

The user may need to complete:

```text
username/password
SSO
Microsoft or Google identity provider
MFA
SMS or authenticator approval
CAPTCHA
passkey
security key
consent screens
```

Codex must preserve the same browser session.

Resume automation when either:

1. the user says login is complete, or
2. the browser clearly shows the authenticated application page and the user has returned control to Codex.

If authentication failed, remain stopped and let the user resolve it.

---

## Phase 3: Reach the application form

After login, continue from the authenticated session.

Depending on the SuccessFactors deployment, Codex may need to click controls such as:

```text
Apply
Apply Now
Continue Application
Start Application
My Candidate Profile
Next
Continue
```

Proceed until the CV upload control or application form is visible.

Do not submit the application.

---

## Phase 4: Upload `cv.pdf`

Find the site's Resume or CV upload control and upload:

```text
cv.pdf
```

Possible labels include:

```text
Resume
CV
Upload Resume
Upload CV
Resume/CV
Attachments
Candidate Profile
```

After upload, SuccessFactors may automatically parse the PDF and populate sections such as Experience, Education, Skills, or Languages.

Wait until parsing has completed.

Indicators that parsing may still be running include:

```text
loading spinner
"Parsing resume"
"Processing"
"Extracting information"
disabled Continue button
new records still appearing
section refreshes
background save notifications
```

Do not start reconciliation while parser updates are still occurring.

Once parsing has stopped, the parsed information becomes disposable temporary data.

---

# Source of truth after upload

After `cv.pdf` has been uploaded, the source hierarchy is:

```text
1. cv_as_excel.xlsx    AUTHORITATIVE
2. SuccessFactors UI  TARGET TO BE CORRECTED
3. cv.pdf             ATTACHMENT ONLY
```

This means:

```text
Excel says A, website says B   -> use A
Excel says A, PDF parser says B -> use A
Excel has a record, website does not -> add it
Website has a parser-created record absent from Excel -> remove it when possible
Excel leaves a field blank -> do not invent a value
```

Codex must never reason that a website value is "probably more correct" than the workbook.

# Reconciliation algorithm

## Preferred strategy: rebuild each managed repeatable section from Excel

For sections where SuccessFactors permits deletion and recreation:

1. Read the Excel sheet into memory.
2. Wait until the site's CV parser is finished.
3. Open the corresponding SuccessFactors section.
4. Delete all parser-generated records in that managed section.
5. Create one site record for every nonblank Excel row.
6. Fill every supported field from the Excel row.
7. Save each record or the full section, depending on the site.
8. Re-read the saved section.
9. Compare it with Excel.

This is preferred because it removes uncertainty caused by the website's CV parser.

## Fallback strategy: update in place

If records cannot safely be deleted:

1. Read all existing website records.
2. Match them conservatively using the record identities defined above.
3. Overwrite every supported field in a matched website record with the Excel value.
4. Add Excel records that are missing from the website.
5. Delete unmatched parser-created website records if the UI permits deletion.
6. Re-read the section and compare against Excel.

Never use fuzzy matching to merge two genuinely different Excel records.

# Handling website variations

SuccessFactors implementations differ significantly between employers.

Do not assume a fixed DOM structure or fixed set of sections.

Prefer interaction targets in this order:

1. accessible role + accessible name
2. visible section heading
3. associated field label
4. `aria-label`
5. stable input name or ID
6. nearby text

# Date handling

Normalize workbook dates only as required by the target controls.

Examples:

```text
2024-06    -> June 2024
Jun 2026   -> June 2026
May 1 2026 -> May 1, 2026
Present    -> Current / Ongoing checkbox when available
```

Rules:

1. Preserve the actual month and year.
2. If the target accepts only month/year, omit the unsupported day.
3. If `End=Present`, use the site's current/ongoing checkbox where available.
4. Never invent an end date for an ongoing item.
5. Convert Excel date serials through the workbook's date system.

---

# Location handling

If the site has one free-text Location field, copy the Excel value exactly.

If the site separates City and Country, split only obvious `City, Country` values.

Examples:

```text
Luxembourg, Luxembourg -> City: Luxembourg | Country: Luxembourg
Lodz, Poland           -> City: Lodz       | Country: Poland
Madrid, Spain          -> City: Madrid      | Country: Spain
```

Do not split ambiguous values such as:

```text
Remote
Remote / Lodz, Poland
Multiple locations
```

If a required dropdown cannot be matched confidently, leave that record unresolved and report it instead of guessing.

# Saving strategy

SuccessFactors may save:

```text
per field
per record
per section
on Next
through autosave
```

After editing a section:

1. trigger the site's normal save mechanism
2. wait for the save to complete
3. reopen or re-read the section after the save cycle, page refresh, collapse/expand, or navigation has completed
4. verify the persisted values against Excel, not only the pre-save DOM values

Do not assume a click succeeded merely because the form closed, the DOM looked correct before saving, or SuccessFactors showed a save confirmation. A save confirmation proves only that the site accepted a draft save request; it does not prove every field value persisted.

For every managed repeatable section, the post-save verification must check:

```text
row count after save
first and last saved row identities
all required text fields are nonblank
dropdowns show committed site values, not only typed text
date controls still show the intended dates
section-level required-field warnings are gone unless intentionally unresolved
```

If any text field becomes blank after saving, re-enter that section using normal typed input events, tab out of each field, save again, and repeat the post-save verification. Do not report a section as complete until the values survive a save and re-read.

---

# Verification pass

After all available workbook-backed sections have been processed, perform a final verification.

For every supported section, produce one of these statuses:

```text
MATCHED
PARTIAL - site does not expose all Excel fields
BLOCKED - a required dropdown/value could not be mapped safely
UNSUPPORTED - the site does not contain this section
```

The application is considered correctly prepared only when there are no unexplained differences between Excel and the website for fields the site actually supports.

The final verification must be performed against the saved application state. If the page regenerates field IDs after saving, remap the section containers and controls from the current page before checking values. Do not rely on stale IDs, stale row maps, or values captured before the last save.

Examples of acceptable differences:

```text
Excel has a day but site accepts only month/year
Excel has several URLs but site accepts only one
Excel section does not exist in this employer's SuccessFactors form
```

Examples of unacceptable differences:

```text
website kept parser-generated employer instead of Excel employer
website title differs from Excel title
website omitted an Excel experience even though Add Experience is available
website retains a parser-created record absent from Excel
website changed a CEFR language level without an explicit mapping
```

---

# Final stopping point

Once the form has been corrected from `cv_as_excel.xlsx`:

1. Save all editable sections.
2. Navigate to the review step if that does not itself submit the application.
3. Report what was filled.
4. Report unsupported or blocked fields.
5. Stop before the final irreversible application submission.

Only click the final `Submit Application`, `Submit`, or equivalent button when the user explicitly asks Codex to submit.

# Lessons learned from live SuccessFactors runs

These observations are generic implementation notes from real SuccessFactors applications. Apply them only when the current site behaves the same way.

1. Some tenants require expiration dates for certifications even when the workbook has no expiration column. Do not invent a date by default. Ask the user for a policy first; if the user confirms the certifications do not expire and approves a placeholder, use that placeholder consistently and report it.
2. Some repeatable sections have silent row caps. The Add button may remain visible but stop creating new rows, or become hidden after the limit is reached. Fill rows in workbook order until the actual site limit is reached, then stop. Do not force hidden controls, dispatch synthetic clicks, or keep retrying after the observed row count no longer increases. Report the remaining workbook rows as partial due to site capacity.
3. Country dropdown fields may not save from typed text alone. When a country is required, open the dropdown and select the exact matching option so the field has the site's internal value, then re-check that the required-field warning is gone.
4. Experience rows can differ in how they tolerate blank end dates. Preserve ongoing roles without inventing end dates where the site accepts blank end dates; for past roles, provide the workbook end date. If only some rows allow blank end dates, use those rows for current roles and report the limitation.
5. Month-only workbook dates may need day-level values when the SuccessFactors control requires `dd/mm/yyyy`. Preserve the month and year; use a consistent first-day convention for starts and a sensible end-of-month convention for ends only when the workbook lacks the day and the target requires one.
6. A successful draft save may be shown as a page-level confirmation such as "El borrador de solicitud de empleo se ha guardado correctamente." Treat this as useful evidence, but still scan visible sections for required-field warnings before final handoff.
7. Do not complete consent, diversity, demographic, referral-source, work-authorization, salary, or other job-specific questions from parsed profile values. Leave them for the user unless the user provides explicit answers.
8. Some text inputs may appear filled in the DOM but fail to persist after a draft save when set with direct automation APIs. For these tenants, click the field, select existing text, type the value through normal input events, tab out, save, reopen the section, and verify the saved value. This is especially important for repeatable text fields such as certification title, certification description, institution, job title, and company.
9. When a saved section shows dates but missing text, treat it as a persistence failure, not as completed work. Repair the affected text fields, save again, and verify after the repair save. Do not continue to later sections or final handoff while a managed section still shows required-field messages caused by fields that should have been filled from Excel.
